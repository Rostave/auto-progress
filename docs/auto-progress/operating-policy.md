# 自动维护运行策略

本文记录当前可调整的运行规则。项目中的具体授权最终以仓库内的项目策略为准。

## 插件组成

- 通用能力打包为一个 `auto-progress` Codex 插件，而不是复制到各仓库的单一 skill。
- 插件包含四个 skill：
  - `maintain-project`：实现维护批次、每日自动维护和人工提前运行的核心流程。
  - `discover-improvements`：只能人工显式调用、创建改进发现 PR 的候选项发现流程。
  - `configure-auto-progress`：`init`、`enable`、`pause`、`resume`、`status`、`export-status` 和历史管理。
  - `queue-directed-improvement`：只能人工显式调用的人工指令录入入口。
- 插件共享配置校验、ID 生成、运行账本、Git 安全检查和报告生成脚本，以及项目配置、改进项、拒绝记录、运行记录和 PR 正文模板。
- Unity 仓库只保存项目策略与项目文档，不复制插件实现。
- Unity MCP 通过可选适配器接入，不绑定某一个具体 MCP 实现；适配器不可用时跳过 Unity 验证并保留 Draft PR。
- 插件安装一次即可服务多个受管项目；各项目的配置、账本、许可、租约和 PR 状态仍然隔离。

## 分支与 PR

- 首次启用受管项目时，由人工指定基准分支。
- 工作分支从基准分支创建。
- 自动 PR 只能合回创建该工作分支时使用的基准分支。
- 项目策略、人工指令项和单次运行均不得设置独立的 PR 目标分支。
- 系统不提供 PR 目标分支覆盖选项，也不允许从分支 A 创建工作分支后向分支 B 创建自动 PR。
- 自动 PR 只能由人工合并。
- 所有自动 PR 必须以 Draft 状态创建；即使只是文档或注释改动，也不得例外。
- Codex 不得仅凭 C# 编译结果、Unity 进程存在或日志推测将 Draft PR 标记为 Ready for review。
- 只有人工，或满足本文 Unity MCP 验证契约的自动验证，才能将 PR 转为 Ready；合并仍只能由人工决定。
- 每个受管项目最多同时存在一个未处理的实现 PR 和一个未处理的改进发现 PR；两类 PR 可以并存，但同类不得创建第二个。
- 存在未处理的实现 PR 时，`implement-batch` 不选择新的改进项，只检查该实现 PR 的 CI、冲突和审查反馈；这不阻止人工触发 `discover-improvements`。
- 存在未处理的改进发现 PR 时，`discover-improvements` 正常停止；这不阻止 `implement-batch` 从基准分支已经合入的权威改进项中选择维护批次。
- 创建任一类型 PR 前，必须查询另一类型未处理 PR 的变更路径，并与本次实际或预计变更路径比较；存在路径重叠时停止创建并交由人工决定，不得自行调整、合并或解决冲突。
- 改进发现会话只读取远端基准分支，不读取未合并实现 PR 的代码；实现维护只选择已经合入基准分支的权威改进项，不读取未合并改进发现 PR 中的候选项。
- 两类 PR 创建后出现的任何 Git 冲突都只能由人工解决。

### GitHub 集成

- 第一版只通过 Git 和 GitHub CLI进行 push、PR 与远端状态操作。
- 工作分支通过普通 Git push 推送，不得 force-push。
- Draft PR 使用 `gh pr create --draft` 创建。
- PR、审查和 CI 状态通过只读 GitHub CLI或 GitHub API查询。
- GitHub 凭据只由 GitHub CLI 的凭据存储管理，不得写入仓库配置、运行账本或日志。
- 身份验证或权限预检失败时，应在 commit 前停止。
- commit 或 push 已经发生后创建 PR 失败时，进入待恢复工作。

### 自动 PR 审查反馈

- 处理已有自动 PR 的反馈仍需要当个维护日的运行许可。
- 反馈处理使用新的运行 ID，继续引用原改进项 ID和原工作分支。
- 明确、可执行且仍在原改进项范围内的审查意见可以自动修改、重新验证、commit 并 push。
- 新 commit 或 push 后，当个维护日立即视为完成。
- 要求扩大范围或涉及不可豁免修改的意见不得自动实施，必须报告阻断原因。
- 含糊的意见不得自行猜测；Codex 可以在 PR 中请求澄清。
- Codex 可以在 PR 留一条简洁回复，说明已处理、无法处理或需要澄清。
- Codex 不得自行 resolve 审查会话、dismiss review、关闭或合并 PR。
- 没有新反馈且 CI 正常时，只更新运行账本，不制造 commit 或 PR 评论。
- 审查修复仍受相应改动预算、C# 编译门槛和 Unity 未验证声明约束。

### 自动 PR 内容

- 一个自动 PR 承载一个维护批次；批次中的每个改进项必须保持独立改进项 ID、验收条件和 commit。
- 正文开头必须显示：`⚠ 未经过 Unity Editor、Play Mode、场景或资源验证`。
- 正文必须包含 C# 编译结果、批次及逐项改动预算使用、全部改进项 ID、运行 ID和运行记录链接。
- 使用人工指令、拒绝清单豁免或其他显式豁免时，必须在正文中披露。
- 正文必须提示审查者：如不希望后续再次出现该方案或类似方案，需要按改进项 ID 将其加入拒绝清单，并描述排除规则与适用范围。

### 自动 PR 冲突

- 自动 PR 与基准分支发生冲突时，只能由人工解决。
- 每日自动化不得 rebase、merge、解决冲突或 force-push；人工指令项也不得豁免该限制。
- 检测到冲突后必须报告冲突文件、与当前改进项的关系和建议处理方式。
- 当个维护日记录为 `skipped: merge_conflict`，不得选择新的改进项。
- 人工解决并 push 后，后续获准运行可以继续检查 PR、CI 和审查反馈。

### Git 作者身份

- `/configure-auto-progress enable` 必须读取并展示仓库当前有效的 `git user.name` 与 `git user.email`，由人工确认该身份及邮箱关联关系。
- 确认结果保存在本机自动化配置，不因本功能额外把私人邮箱写入仓库配置。
- 每次 commit 前必须重新校验当前 Git identity；缺失或与已确认身份不符时停止，不得 commit。
- 每日自动化不得修改全局、仓库或 worktree 的 Git identity。
- 不得创建空 commit、回填历史日期或伪造 commit 时间；使用真实执行时间。
- commit message 与 PR 必须注明自动维护来源，并引用对应改进项 ID和运行 ID。
- 初次实现应尽量使用一个包含代码、测试、改进项文档和运行记录的原子 commit；后续审查修复可以追加新 commit。
- 工作分支 commit 只有在 PR 被人工合入基准分支后，才可能满足 GitHub 贡献图的分支条件。
- 切换为机器人或其他身份必须由人工重新执行配置流程，日常任务不得自行决定。

## 原项目目录租约

- 每日自动维护和人工提前运行在原始 Unity 项目目录中本地执行，不创建第二份 Unity 项目或 `Library`。
- 人工批准运行即授予当次工作区租约；租约期间其他人工或自动工作流不得使用该目录。
- 开始前必须确认 Git 没有 staged、tracked 或 untracked 人工改动，没有正在进行的 merge、rebase、cherry-pick 等操作，也没有其他 AutoProgress 运行。
- Unity Editor 已打开时，还必须通过 Unity MCP确认没有未保存的 Scene/Asset，并且 Editor 不在 Play Mode、Build、Import 或 Compile；MCP 不可用时不得在打开的 Editor 上开始运行。
- 任一前置条件不满足时当天跳过。自动化不得 stash、保存、reset、清理或覆盖人工内容。
- 取得租约后记录运行前的原始 branch 与 HEAD，fetch 远端，并从最新的 `origin/<基准分支>` 创建和 checkout 工作分支。
- fetch 失败、远端基准分支不存在或检测到无法确认的历史改写时，当天跳过。
- 恢复运行必须 checkout 并继续使用原工作分支，不得从更新后的基准分支重新实现同一改进项。
- 运行结束后必须尝试 checkout 回记录的原始 branch/HEAD；Unity Editor 已打开时，通过 Unity MCP再次 Refresh 回原项目状态。
- 恢复原始 branch/HEAD 是清理义务，即使达到运行时间上限也必须尝试。
- 恢复失败时不得 force、reset 或覆盖文件；必须保留现场、报告当前 branch/HEAD，并阻止后续自动运行直到人工恢复。

## AutoProgress 任务类型与每日活动额度

- AutoProgress 以可扩展任务类型表达每天主要执行的工作，而不是把所有行为固定为代码实现维护。
- 第一版包含：
  - `implement-batch`：从权威改进池选择并实现一个维护批次。
  - `discover-improvements`：通过审查切片寻找候选项并创建改进发现 PR。
- `implement-batch` 由 `$maintain-project` skill 执行，可由每日调度或人工提前运行触发。
- `discover-improvements` 由 `$discover-improvements` skill 执行，只能由人工显式调用；每日调度、`$maintain-project` 和其他任务类型不得隐式调用。
- 每个任务类型对应一个独立 skill，并通过共享的确定性脚本执行额度占用、账本追加和通用 Git/GitHub 预检。
- `$configure-auto-progress` 与 `$queue-directed-improvement` 是人工管理入口，不属于每日任务类型；它们本身不占用每日活动额度。
- 未来新增任务类型时必须新增独立 skill 并接入共享额度协议，不得在现有 skill 中通过未声明的隐式分支绕过调用权限。
- 所有现有及未来任务类型都必须竞争同一个每日活动额度；一个维护日最多只有一个任务类型可以开始核心工作。
- 每个任务类型必须声明资格检查、触发方式、工作区策略、时长上限、成功与失败语义、产物、恢复方式和是否允许安全重试。
- 资格检查不占用每日活动额度。已有未结束发现 PR、库存已达目标或其他无需开始核心工作的正常退出不得阻止当天其他任务类型。
- 任务类型通过资格检查并准备开始核心工作时，必须原子写入 `daily_allowance_claimed` 账本事件，包含维护日、任务类型和任务实例标识。
- 当天已经存在 `daily_allowance_claimed` 时，其他任务类型不得开始；只有同一任务实例按该类型规则允许的安全重试可以继续。
- 一个任务类型占用额度后，即使零产出、失败或超时，也不得切换到另一任务类型。
- 任务类型占用每日活动额度不等于维护完成；各任务类型分别记录自己的结果，只有 `implement-batch` 沿用工作分支 commit/push 的实现维护完成语义。
- 未来新增任务类型必须遵守每日活动额度协议，不得通过独立 automation、独立账本或更换任务名称绕过单日互斥。

## 调度

- 项目策略中的时区使用 IANA 标识 `Asia/Shanghai`，表示中国标准时间（UTC+8）。
- 改进项 ID 的日期按项目策略时区生成。
- 每天（包括周末）的启动窗口为 `19:30` 至 `20:00`。
- 每次运行必须先取得当次运行许可，不能仅因进入启动窗口便自动开始项目修改。
- `19:30` 的 Codex automation 只进入许可阶段，不创建运行 ID，也不取得工作区租约。
- `19:30` 发出运行许可请求。人工可以立即批准、跳过，或将请求推迟 10 分钟。
- 延后只安排同一许可任务的下一次提醒，不得创建重复的每日 automation。
- 运行许可可以继续推迟，但不得超过 `20:00`；截止前没有获得批准时，记录许可超时事件并在当天跳过，但不算已启动运行。
- “延长 10 分钟”只延长等待启动的时间，不延长已经启动任务的运行时长。
- 只有人工批准后才创建运行 ID、尝试取得工作区租约并执行 Git 与 Unity 前置检查。
- `20:00` 只限制最晚许可和启动时间；已经获批并启动的运行可以在此后继续。
- 项目策略必须设置 `max_run_minutes`，默认值为 `60`。
- 达到运行上限时，如果尚未产生 commit 或 push，停止并报告，下一维护日可以重新运行。
- 达到运行上限时，如果已经产生 commit 或 push，当天视为完成，下一维护日按待恢复工作处理。
- 维护日按项目策略时区划分，提前运行与窗口调度使用同一个维护日键去重。
- 人工可以在当个维护日的启动窗口开始前触发提前运行；主动触发本身视为授予当次运行许可。
- 人工提前运行直接创建运行 ID并尝试取得工作区租约。
- 提前运行完成后，当个维护日的启动窗口不再请求许可或启动第二次运行。
- 许可阶段调用 `pause` 时取消当日请求；运行 ID已经创建且租约已取得后，暂停不影响当前运行。
- 同一受管项目不得并发执行两个自动维护运行。
- `19:30` 定时任务在请求 `implement-batch` 许可前必须检查每日活动额度；当天额度已被任何任务类型占用时，只报告任务类型和已有结果并停止。
- 工作分支一旦产生 commit 或发生 push，任一条件满足即视为当个维护日已经完成；即使尚未创建 PR，当天也不得再次自动运行。
- 上述“完成”只禁止启动当个维护日的第二次运行，不中断当前运行继续进行 push、创建 PR、Unity MCP 验证、写入账本和恢复原工作区。
- 在工作分支产生 commit 或 push 之前发生的纯技术故障，可以在启动窗口内重新请求一次运行许可。
- 工作分支产生 commit 或 push 后发生故障时，不得在同一维护日自动重试；必须报告工作分支、已有 commit、远端状态以及 PR 是否创建。
- 新维护日开始时如果存在待恢复工作，当天取得许可后必须优先执行恢复运行。
- 恢复运行只能检查并验证现有改动、push 现有工作分支以及创建 PR，不得选择或实现新的改进项。
- 待恢复工作成功创建 PR 后，当个维护日视为完成。
- 恢复运行仍失败时必须报告状态。只要本次恢复运行没有产生新的 commit 或 push，可以在当日启动窗口内进行一次安全重试。
- 待恢复工作存在期间，不得创建新的工作分支。

## 改进池

- 维护运行只从权威改进池选择一个维护批次，不负责发现新的普通自动候选项。
- 一个维护批次默认最多包含 `3` 个具备批次兼容性的改进项；找不到兼容项时允许只实现一项，不得为了凑数加入无关改动。
- 批次兼容性要求改进项位于相同或相邻模块、没有范围或行为冲突、能够共享验证路径，并且合计不突破批次预算。
- 维护运行必须依据权威改进项文档中的模块、预计路径、验证方式和兼容性信息组批；不得审查新的代码切片、构思新候选项或为了凑满批次扩大现有改进项。
- 权威改进池中只有一项合格，或没有更多兼容项时，维护运行直接执行较小批次或单项，不得临时调用改进发现入口。
- 每个进入改进池的改进项必须拥有项目内唯一且稳定的改进项 ID。
- 普通自动候选项的发现与改进项实现必须属于不同流程，不得为了填充改进池而启动或计作维护运行。
- 没有合格改进项时跳过，不为日志或 GitHub 活动图制造 commit。
- 构思和记录改进项前，必须先读取拒绝清单；命中其中任一排除规则的候选项不得进入改进池。

### 改进项发现

- 改进项发现只能由人工显式触发的独立改进发现会话执行；每日维护、提前运行和恢复运行不得自动调用。
- 改进发现会话通过审查切片发现自动候选项，不得默认扫描整个项目。
- 审查切片先包含基准分支自上次运行以来修改过的允许范围内 C# 文件，再从允许目录中轮转选择一个模块或文件夹。
- 审查切片默认先选择最多 `30` 个 C# 文件；候选项不足且仍有运行时间时，可以按每轮最多 `15` 个文件继续扩展。
- 一次改进发现会话默认最多审查 `60` 个 C# 文件且所选文件合计不得超过 `12000` 行源码；触及任一硬上限后不得继续扩大切片。
- 达到本次候选项上限、耗尽运行时间或触及任一审查硬上限时停止发现；不得为了凑满目标库存而降低候选项准入标准。
- 同一模块默认 `30` 个维护日内不重复全面审查，除非它近期发生变化或存在编译错误。
- 第三方、Vendor、Packages、生成代码以及项目策略排除路径不得进入审查切片。
- 人工触发时可以指定一个项目策略允许路径内的发现关注范围；指定后以该范围代替审查游标决定本次审查切片。
- 人工明确指定发现关注范围时可以越过该模块的轮转冷却期，但不得绕过文件数、时间、允许与排除路径、拒绝清单、去重或候选项准入门槛。
- 未指定发现关注范围时，必须按审查游标选择标准审查切片。
- 本次审查路径和审查游标只记录到本地运行账本，不制造仓库 commit。
- 项目策略通过 `discovery.initial_files`、`discovery.expansion_files`、`discovery.max_files`、`discovery.max_source_lines` 和 `discovery.revisit_after_maintenance_days` 配置审查范围；发现会话不设置独立分钟上限，直接复用 `project.max_run_minutes`，默认 `60` 分钟。
- 项目策略通过 `discovery.target_queued_automatic_improvements` 配置普通自动改进项的目标库存，默认值为 `10`。
- 项目策略通过 `discovery.max_new_improvements` 限制每次发现会话新增的合格改进项，默认值为 `10`。
- 项目策略通过 `discovery.closed_pr_cooldown_maintenance_days` 配置发现 PR 关闭后的候选项冷却期，默认值为 `7` 个维护日。
- 发现会话开始时先统计远端基准分支中来源为普通自动发现且状态为 `queued` 的权威改进项；人工指令项、编译修复项和未合并发现 PR 中的候选项不计入目标库存。
- 普通自动 `queued` 改进项数量达到目标库存时正常结束，不创建空分支、空 commit 或空 PR。
- 本次最多新增 `min(目标库存缺口, max_new_improvements)` 个合格候选项。
- 目标库存是停止发现的软目标，不构成最低产出要求；审查切片、时间预算、去重或准入门槛可以使本次新增项少于目标缺口或为零。
- 改进发现会话不实现任何改进项；通过准入并正式进入改进池的候选项状态均为 `queued`。
- 新候选项必须与当前排队项、已实现项、冷却中的关闭 PR 和拒绝清单进行去重。
- 未通过准入的随想不得写入改进池。
- 改进发现会话不取得实现维护的运行许可，也不生成维护日完成事件，但开始时必须占用当天每日活动额度。
- 发现会话开始核心审查前，必须通过通用协议写入 `daily_allowance_claimed`，任务类型为 `discover-improvements`，随后记录 `discovery_started`。
- `discover-improvements` 占用额度后，当天尚未开始或仍等待人工许可的定时、延后或提前 `implement-batch` 必须取消。
- 定时维护启动前必须检查当天的通用额度事件；已由 `discover-improvements` 或未来其他任务类型占用时，只报告占用类型并停止，不得再次请求实现维护许可。
- 改进发现会话最终新增项少于上限、零新增、失败或超时，都不将其改写为维护完成事件。
- 每次改进发现会话在独立工作分支中创建一个只包含候选改进项文档的 Draft 改进发现 PR，不得包含候选项的功能实现。
- 改进发现 PR 只能以项目配置的基准分支为目标，不得自动合并。
- 候选项只有经人工审查并随改进发现 PR 合入基准分支后，才成为权威改进池中可供维护运行选择的 `queued` 改进项。
- 未合并、已关闭或仍处于 Draft 的改进发现 PR 中的候选项不得被维护运行选择。
- 改进发现 PR 被关闭但未合并不构成拒绝；其中候选项进入项目策略配置的发现冷却期。
- 发现冷却期间不得再次提出相同或实质相似的候选项；冷却结束后，只有代码证据或方案发生实质更新时才能再次提出。
- 再次提出时必须沿用原改进项 ID、引用原发现 PR 并说明更新内容；不得创建新 ID 将同一候选项伪装成新点子。
- 未发生实质更新时继续按重复项排除；只有人工写入拒绝清单才会永久阻止该方案及命中排除规则的相似方案。
- 人工需要立即推进该方案时，可以通过人工指令改进项入口实施，不需要等待发现冷却期。
- 每个受管项目最多允许一个状态为 Open 或 Draft 的改进发现 PR。
- 新的改进发现会话发现已有未结束的改进发现 PR 时，必须报告该 PR 并正常停止；不得追加候选项、修改其分支或创建第二个发现 PR。
- 未处理的实现 PR 不直接阻止改进发现会话；发现会话仍只从最新远端基准分支取证，并在创建 PR 前执行跨类型路径重叠检查。
- 改进发现 PR 产生的 commit、push 和 PR 事件属于发现会话，不得写作维护日完成事件，也不得影响维护日去重。
- 改进发现 PR 必须提示审查者：如需阻止某项或实质相似方案再次被发现，应按改进项 ID 由人工写入拒绝清单。
- 改进发现会话必须先 fetch，并从最新 `origin/<基准分支>` 创建独立轻量 worktree；不得从人工开发目录中的未提交状态或本地领先提交发现候选项。
- 改进发现会话不取得原始 Unity 工作区租约。原始项目目录是否干净、Unity 是否打开，不构成发现会话的阻断条件，人工可以继续在原目录开发。
- 发现 worktree 不得初始化或复制 Unity `Library`，不得调用 Unity MCP，也不得运行配置的 C# 编译验证步骤。
- 发现阶段只记录支持候选项的代码证据和未来实现时应执行的验证方法，不得把未执行的编译或 Unity 检验描述为已通过。
- 改进发现 PR 创建或会话正常结束后，必须移除临时 worktree；远端发现分支和 Draft PR 按人工审查流程保留。

### 改进项状态

- `queued` 表示等待实现。
- `implemented` 表示对应实现 PR 已进入基准分支。
- `cancelled` 表示由人工取消。
- 永久拒绝只由拒绝清单表达，不增加 `rejected` 状态。
- 实现 PR 可以在同一 PR 中把选中项写为 `implemented`；该文件只有随代码合并进入基准分支后才成为项目事实。
- 人工指令项因前置条件无法执行时继续保持 `queued`，阻断原因只进入运行账本和 `status`；不得为修改状态单独制造文档 PR。

### 自动候选项准入与排序

每个自动发现的候选项记录：

- `value`：`0` 表示无明确价值，`1` 表示局部可维护性，`2` 表示调试或开发体验，`3` 表示正确性或可靠性。
- `confidence`：`0` 表示猜测，`1` 表示间接迹象，`2` 表示明确代码证据，`3` 表示测试或静态分析证据。
- `risk`：`0` 表示文档或私有局部影响，`1` 表示有限行为影响，`2` 表示跨组件影响，`3` 表示序列化、公开接口或运行时高风险。
- `estimated_size`：预计修改文件数与变更行数。
- `module`：候选项所属的稳定模块或功能区域。
- `evidence_paths`：支持候选项判断的实际证据路径。
- `expected_paths`：预计实现时需要修改的路径。
- `validation_profile`：预计共享的编译、测试或人工验证方式。
- `batch_affinity`：与其他改进项组批时使用的兼容性标签和已知冲突。
- `discovered_at_base_sha`：完成发现时所依据的远端基准分支提交。
- `evidence_blob_shas`：证据路径在发现时对应的 Git blob SHA。

自动候选项必须同时满足：

- `value >= 1`
- `confidence >= 2`
- `risk <= 1`
- 未命中拒绝清单
- 未超过改动预算硬上限
- 具有明确验证方法

通过准入后依次按价值更高、信心更高、风险更低、预计改动更小、等待时间更久进行排序，不计算可让高价值抵消高风险的单一总分。

纯审美格式调整或仅以“更现代”为理由的重写不构成明确价值。没有候选项通过准入时，改进发现会话以零新增项正常结束。

### 候选项新鲜度

- 维护任务组批前必须比较改进项记录的 `discovered_at_base_sha`、`evidence_paths`、`expected_paths` 和 `evidence_blob_shas` 与当前远端基准分支。
- 所有相关路径未变化时，候选项通过新鲜度检查，不得为确认其价值重新扫描模块。
- 相关路径发生变化时，只能读取改进项已经记录的证据和预计路径进行有界复核，不得扩展审查切片或构思替代候选项。
- 原判断仍成立时可以继续实施，并在实现 PR 中更新发现基准和证据。
- 原判断失效、范围已经消失或需要扩展到未记录路径才能判断时，不得实施；运行账本记录 `candidate_stale`，本次可以从权威改进池选择下一项。
- `candidate_stale` 不修改基准分支中的改进项文件，也不触发单独文档 PR；后续 `$discover-improvements` 负责在发现 PR 中刷新或取消该项。
- 被当前账本标记为陈旧、且改进项文档自标记后未更新的普通自动项，不计入有效目标库存和批次就绪项。
- 自动维护不得把新鲜度复核变成候选发现，也不得临时创建新 ID 替换陈旧项。

### 人工指令改进项

- 人工可以向改进池添加人工指令改进项。
- 人工指令改进项优先于自动发现候选项。
- 人工指令改进项可以不满足自动候选项的价值、信心或风险准入条件。
- 人工指令改进项完全豁免拒绝清单。即使其内容命中或等同于拒绝记录，也允许进入选择和实现流程。
- 自动 PR 必须披露人工指令项命中了哪些拒绝记录，但该披露仅供审查，不构成阻断条件。
- 拒绝清单继续约束所有由 Codex 自主发现或构思的候选项。
- 人工指令改进项的实现和验收仍遵守已确定的编译、PR、人工合并和报告策略。
- 除拒绝清单和自动候选项准入条件外，“人工指令”不构成对其他自动维护规则的笼统豁免；其余可豁免与不可豁免约束必须逐项定义。
- 人工指令项只有在运行开始前已经存在于最新的 `origin/<基准分支>` 时才有效。
- 日常自动化不得创建人工指令项，也不得把普通改进项升级为人工指令项。
- 执行人工指令项时，Codex 可以更新其状态并追加执行结果，但不得改写人工指定的目标、范围和豁免内容。
- 在自动工作分支中临时创建或升级的人工指令项无效。

#### 人工指令改动预算

- 人工指令改进项自动豁免普通改动预算的建议上限。
- 没有显式 `budget_override` 时，人工指令项仍受普通改动预算硬上限约束。
- `budget_override` 必须逐项给出新的文件数或行数上限，并说明突破普通硬上限的理由。
- 单个人工指令项即使声明 `budget_override`，仍不得超过项目策略中的人工指令绝对上限。
- 默认人工指令绝对上限为：
  - C# 与测试文件 `10` 个。
  - C# 与测试新增行数与删除行数之和 `500` 行。
  - 包含文档和必要 `.meta` 在内的全部变更文件 `15` 个。
- 超过人工指令绝对上限的工作不适合每日自动任务。必须先由人工通过独立配置 PR 修改项目策略，或改用一次性人工 Codex 任务。
- 每次运行仍只能执行一个人工指令项，不得通过叠加多个指令规避预算。

#### 人工指令范围豁免

人工指令项可以显式豁免：

- 自动候选项的 `risk <= 1` 准入门槛。
- 跨组件 C# 修改限制。
- 人工指定范围内的公共 C# API 修改限制。
- Unity 生命周期方法及执行顺序相关的 C# 修改限制。
- 项目默认允许路径之外、但仍属于 C#、测试或文档的路径限制。
- 普通改动预算，但必须遵守人工指令改动预算规则。

以下限制不得由每日自动任务中的人工指令项豁免：

- 修改 `.unity`、`.prefab`、`.asset` 等 Unity 序列化资源。
- 修改序列化字段名称或类型。
- 修改 `ProjectSettings/`、`UserSettings/`。
- 修改 `Packages/manifest.json`、`packages-lock.json`。
- 修改 `.asmdef`、`.asmref`。
- 修改插件、平台构建、发布或 CI 配置。
- 修改凭据、认证、权限或密钥相关配置。
- 修改 Unity/Rider 生成文件。
- 删除测试、降低断言、忽略编译错误或绕过 C# 编译门槛。
- 绕过人工 PR 审查或 Unity 未验证声明。

需要上述不可豁免范围的工作必须改用一次性人工 Codex 任务，不得进入每日自动维护流程。

#### 人工指令队列优先级

- 人工指令项优先于所有尚未开始的自动候选项，但不抢占已经存在的工作。
- 已有未处理的实现 PR 时，人工指令项必须等待该 PR 被人工合并或关闭；改进发现 PR 本身不阻止人工指令项，但仍受跨类型路径重叠检查约束。
- 存在待恢复工作时，必须先完成恢复，或由人工明确处理并放弃旧工作分支。
- 已有运行正在执行时，不得并发执行或为了人工指令项中断当前运行。
- 人工指令项进入远端基准分支后，成为下一次具备执行条件的运行中的最高优先级项。
- 每日自动化不得自行关闭、废弃或覆盖旧 PR，为人工指令项让路。
- 确需抢占的工作必须由人工先处理现有状态，或改用一次性人工 Codex 任务。
- 基准分支存在 C# 源码编译错误时，恢复 C# 编译优先于与错误无关的人工指令项。
- 人工指令项本身能够恢复这些编译错误时，可以直接作为编译修复项执行。
- 无法在允许范围和预算内恢复编译时，当天跳过并报告；无关人工指令项保持 `queued`，不得用来绕过编译修复优先级。

完整执行优先级为：

1. 已有自动 PR 或待恢复工作。
2. 恢复基准分支的 C# 编译。
3. 人工指令改进项。
4. 通过准入的普通自动候选项。

批次隔离规则：

- 已有自动 PR 或待恢复工作使用恢复运行，始终独占维护批次，不得选择新改进项。
- 恢复基准分支 C# 编译的改进项始终独占维护批次。
- 人工指令改进项默认独占维护批次，不与其他人工指令项或普通自动改进项组合。
- 只有普通自动改进项可以由 Codex 自动组成最多 `3` 项的维护批次。
- 第一版不得自行推断人工指令项适合批处理；未来只有人工显式授权的批处理规则才能改变该限制。

#### 批次部分交付

- 维护批次按排序逐项实现，每个改进项使用独立 commit。
- 某项在 commit 前无法完成时，只能精确撤销当前任务对该项造成的未提交修改；该项保持 `queued`，不得影响此前成功项。
- 某项已经 commit、但导致最终验证失败时，必须先在原项范围和预算内尝试修复。
- 无法修复时，允许在任何 push 之前使用 `git revert` 撤销本次运行自己创建的该项 commit；不得 revert 基准分支、历史提交、人工提交或其他运行的 commit。
- revert 后必须重新执行最终完整验证；验证通过的其他改进项可以作为成功子集继续 push 并创建同一个 Draft PR。
- PR、运行记录和账本必须逐项列出 `delivered`、`deferred` 或 `reverted` 结果及原因；未交付项不得标记 `implemented`。
- 一个批次中的失败项不得由临时发现、扩展范围或从权威池外选择的新项替补。
- 无法精确隔离失败项、无法安全恢复干净工作区或最终验证仍失败时，停止并进入待恢复工作；不得 reset、force-push、重写历史或猜测性清理。

### 指令录入入口

- 系统必须提供一个与每日维护流程分离的指令录入入口，供人工快速创建人工指令改进项。
- 手动 skill 名称为 `/queue-directed-improvement`，并设置 `disable-model-invocation: true`。
- 指令录入入口只能由人工显式调用；每日自动化及其恢复运行不得调用。
- 手动 skill 负责交互式收集改进目标、原因、影响范围、验收条件、允许路径、请求豁免项、优先级和可选截止日期。
- skill 内部调用专用校验脚本生成改进项 ID、检查冲突、展示命中的拒绝记录并生成规范的 Markdown 文件。
- 每日自动化不得直接调用该校验脚本，以绕过手动 skill 的调用限制。
- 指令录入入口只负责收集、生成和校验人工指令项，不得同时实现该改进项。
- 入口必须在独立 worktree 中创建只包含人工指令文件的配置 PR，不得包含功能代码、拒绝清单修改或自动合并操作。
- 由入口创建的人工指令项必须先进入远端基准分支，之后才可被每日运行识别。

## 项目配置入口

- 系统提供只能由人工显式调用的 `/configure-auto-progress` skill，并设置 `disable-model-invocation: true`。
- `/configure-auto-progress init` 验证 Unity 仓库并收集基准分支、结构化验证步骤、允许与排除路径、改动预算和运行上限。
- `init` 必须检查 `Library/`、`Temp/`、`Logs/`、`obj/`、`UserSettings/`、`.idea/`、`.vs/`、Unity/Rider 生成的 `.csproj`、`.sln` 以及项目构建输出目录的 Git 忽略状态。
- 未被跟踪的生成内容缺少忽略规则时，`init` 可以在配置 PR 中提出经过人工确认的最小 `.gitignore` 补充，不得用通用模板覆盖项目已有规则。
- 生成内容已经被 Git 跟踪时，`init` 不得自动移除或执行 `git rm`；必须阻止启用并要求人工处理。
- 验证步骤依赖被忽略的 `.sln` 或其他本地生成入口时，`enable` 必须确认文件当前存在且步骤实际可执行；缺失时不得猜测生成方式。
- `init` 从人工指定的基准分支创建独立工作分支，生成 `.codex/auto-progress.toml`，并创建只包含配置和必要文档的 PR。
- `init` 不得自动合并配置 PR，也不得启用每日调度。
- `/configure-auto-progress enable` 只能在配置 PR 合并后由人工调用。
- `enable` 必须 fetch 并确认配置存在于远端基准分支，校验验证步骤、Git remote、PR 创建能力和工作分支权限，然后创建每日许可请求与维护调度。
- `enable` 必须检查 GitHub CLI 是否安装并已登录，校验当前账号对 `origin` 仓库拥有 push 和创建 PR 的权限。
- `enable` 不得代替人工执行交互式 GitHub 登录；认证缺失时只报告所需操作。
- `enable` 不立即执行项目修改；第一次运行仍需人工许可或提前触发。
- 重复调用 `enable` 必须更新已有自动化，不得创建重复任务。
- `/configure-auto-progress pause` 暂停每日调度。已处于运行状态的任务继续完成；当日尚未启动时，取消当日许可请求、延后请求和计划运行，并从后续维护日起保持暂停。
- `pause` 保留项目配置、运行历史、待恢复工作和未处理 PR，不删除自动化。
- 暂停每日调度不禁止人工显式提前运行；提前运行本身构成新的人工许可。
- `/configure-auto-progress resume` 恢复每日调度，默认从下一维护日生效，不在恢复当天自动补跑。
- 恢复当天如需执行，必须由人工显式触发提前运行。
- `/configure-auto-progress status` 提供只读状态与统计，不得触发、恢复、取消或修改任何运行。

### 多项目语义

- 每个受管项目拥有独立的 Codex automation、运行账本、工作区租约和许可请求。
- 各项目在启动窗口内分别请求许可；人工可以分别批准、延后或跳过。
- 第一版不提供跨项目控制器，也不自动决定当天维护哪个项目。
- 不同项目可以并行运行；同一项目内部仍严格禁止并发。
- `/configure-auto-progress status` 默认查看当前或指定项目，`status --all` 只读汇总所有已配置项目。
- `pause`、`resume` 和 `purge-history` 默认只作用于指定项目；只有人工显式使用 `--all` 时才批量操作。
- 批量清理历史仍必须逐项目展示范围并确认。

### Status 状态与统计

`status` 默认展示当前状态、当个维护日状态、最近 30 个维护日统计以及全量统计。所有日期按项目策略时区归属。

当前状态至少包含：

- 仓库、基准分支和配置版本。
- 调度状态与下一次许可请求时间。
- 运行锁、当日每日活动额度及其任务类型、未处理的实现 PR、未处理的改进发现 PR 和待恢复工作。
- 基准分支当前普通自动 `queued`、人工指令 `queued`、失效候选项数量，以及未合并发现 PR 中不具权威性的候选项数量。
- 当前库存必须标明读取基准分支与远端 PR 状态的快照时间，不得与所选历史统计区间混为一谈。

当个维护日状态使用以下语义：

| 状态 | 含义 |
| --- | --- |
| `not_started` | 尚未请求许可或人工提前运行 |
| `approval_pending` | 正在等待人工批准 |
| `deferred` | 已延后，等待下次许可请求 |
| `running` | 已取得许可并开始执行 |
| `monitoring_pr` | 已有自动 PR，本日只处理其状态 |
| `retryable_failure` | commit/push 前失败，本日仍可安全重试一次 |
| `completed_pr` | 已成功创建 PR，本日不再运行 |
| `pending_recovery` | 已产生 commit/push 但没有 PR，本日不再运行 |
| `skipped` | 无合格改进项、许可过期或前置条件不满足 |
| `paused` | 本日调度暂停，仍可人工提前运行 |

`skipped` 必须同时展示具体原因。

最近 30 个维护日与全量统计至少包含：

- 启用维护日数。
- `daily_allowance_claimed` 的维护日数，并按 `implement-batch`、`discover-improvements` 和未来任务类型分别统计。
- 许可请求、批准、主动跳过和超时次数。
- 延后事件次数；延后是事件数，不是维护日数。
- 实际启动次数。
- 无改动跳过次数及原因分类。
- `implement-batch` 的运行数、维护批次数，以及改进项 `delivered`、`deferred`、`reverted` 和 `candidate_stale` 数量。
- `delivered` 只表示改进项已进入实现 PR；只有基准分支中状态为 `implemented` 才表示实现已由人工合入。
- `discover-improvements` 的会话数、审查文件数、审查源码行数、提出候选项数、零候选会话数和改进发现 PR 数量。
- 发现会话“提出候选项”不得计作权威 `queued`、`delivered`、`implemented` 或已完成改进。
- 自动候选项与人工指令项的实际执行次数。
- 编译修复次数。
- 产生 commit、push 成功以及 PR 创建、合并、关闭和仍打开的数量。
- 待恢复工作产生及恢复成功次数。
- commit/push 前可重试失败次数。
- 达到运行时间上限次数。
- 各任务类型的成功、跳过、失败、超时、平均耗时及具体原因分类。

统计规则：

- 跳过是正常结果，不计为失败。
- 不计算掩盖不同结果的笼统成功率。
- commit 数不作为质量指标，GitHub 活动图不作为成功判定。
- 数据源不可访问时显示 `unknown`，不得当作 `0`。
- 重试、延后和恢复使用同一个维护日 ID 去重。
- `status` 严格只读；远端状态只允许通过只读查询获得。
- `export-status` 生成的 Markdown 必须使用相同统计口径，并标明历史统计区间与当前库存快照时间。

## 记录与文档

### 本地运行账本

- 每次许可请求、延后、批准、跳过、运行、失败、commit、push 和 PR 事件都自动追加到运行账本。
- 运行账本保存在 Codex 本地状态目录，不进入受管项目 Git。
- 运行账本是 `status` 统计的事实来源；历史事件不得回写修改。
- 写入账本不得制造项目 commit 或工作分支。
- 每个受管项目按月保存追加式 JSONL，目录使用由规范化 GitHub remote 与基准分支生成的项目 ID，不依赖本机项目路径。
- 每条事件必须拥有唯一事件 ID；重试写入按事件 ID去重。
- 事件只记录维护日、运行 ID、任务类型、改进项 ID 列表、状态、耗时和产物引用，不保存代码片段、完整编译日志、Git 邮箱、凭据或本机绝对路径。
- 月度账本默认永久保留，以支持准确的全量统计。
- `pause`、`resume`、重新配置或项目目录被移除均不自动清除账本。
- `/configure-auto-progress purge-history` 只能由人工显式调用，必须展示项目和时间范围并再次确认；每日自动化不得调用。
- 本地账本丢失时，只能从 GitHub PR 与仓库运行记录重建部分历史；`status` 必须标记许可、延后和无改动跳过等统计可能不完整。

### 自动 PR 运行记录

- 成功产生实际改动 PR 时，必须在同一个 PR 中加入 `docs/auto-progress/runs/YYYY.MM.DD-<run-id>.md`。
- 运行记录至少包含维护批次中的全部改进项 ID 与来源、逐项及批次选择理由、运行 ID、工作分支、逐项与合计改动预算、基线与最终验证、Unity 验证状态、拒绝命中与豁免以及结果时间线。
- 运行记录不得尝试写入其自身 commit hash，也不要求写入尚未创建的 PR 编号或 URL。
- 每个改进项使用独立 commit，commit message 引用该改进项 ID和批次运行 ID；PR 正文引用运行记录路径并按改进项列出实际 commit；本地运行账本在产物创建后记录精确 hash、PR 编号和 URL。
- 运行记录、各项 commit、PR 和账本通过全部改进项 ID、运行 ID与工作分支关联。
- 没有实际改动 PR 的跳过日只写本地运行账本，不得为了运行记录创建 commit 或 PR。

### 人工状态报告

- `/configure-auto-progress export-status` 由人工显式调用，按指定时间范围从运行账本生成 Markdown 状态报告。
- 默认行为只预览，或写入独立 worktree 而不 commit。
- 只有人工显式指定 `--pr` 时，才允许创建只包含报告的文档 PR。
- 报告文件保存为 `docs/auto-progress/reports/status-<start>--<end>.md`。
- 状态报告是可再生快照，不是新的统计事实来源。

### 文件与 ID

- 项目策略保存为 `.codex/auto-progress.toml`。
- 当前项目策略版本为 `schema_version = 2`。
- 从旧策略版本迁移只能由人工显式调用 `$configure-auto-progress migrate`；每日任务和其他自动入口不得自动迁移、补写或提交配置。
- 迁移入口必须先展示完整配置差异，取得人工确认后才能修改 `.codex/auto-progress.toml`；迁移结果由人工审查并提交，不得自动 commit 或创建 PR。
- 每日任务读取到 `schema_version = 1` 或其他不受支持版本时，必须在资格检查阶段停止并提示迁移，不得套用新默认值，也不得占用每日活动额度。
- `status` 与账本读取必须继续兼容迁移前产生的历史事件；配置版本变化不得改写旧账本。
- 每个改进项使用独立 Markdown 文件，保存于 `docs/auto-progress/improvements/`。
- 每条拒绝记录使用独立 Markdown 文件，保存于 `docs/auto-progress/rejections/`。
- 改进项 ID 格式为 `IMP-YYYY.MM.DD-xxxxxxxx`，其中末段为 8 位随机十六进制字符，例如 `IMP-2026.07.29-a1b2c3d4`。
- 所有开始核心工作的 AutoProgress 任务实例统一使用 `RUN-YYYY.MM.DD-xxxxxxxx` 格式的运行 ID，并通过必填 `task_type` 字段区分任务类型。
- ID 一经创建便永久稳定；即使对应 PR 被关闭或未合并，也不得复用。
- 同一任务类型在同一维护日内的安全重试沿用原运行 ID，并通过 attempt 编号区分；不得沿用该 ID 切换任务类型。
- 跨日恢复创建新的运行 ID，但继续引用原改进项 ID 与原工作分支。
- 改进项文件至少包含标题、动机、范围、风险、验证方法和状态。
- 拒绝记录沿用被拒绝改进项的 ID，并至少包含拒绝原因、排除规则和适用范围。
- 命中已有排除规则的相似候选项不得创建改进项文件，也不得通过生成新 ID 绕过拒绝清单。

### 工作分支命名

- `implement-batch` 工作分支格式为 `codex/auto-progress/run-yyyy.mm.dd-xxxxxxxx-implement-batch`。
- `discover-improvements` 工作分支格式为 `codex/auto-progress/run-yyyy.mm.dd-xxxxxxxx-discover-improvements`。
- 分支名使用小写并包含完整运行 ID；文档、commit 和 PR 中的正式运行 ID 与改进项 ID 保持大写。
- 工作分支归属于任务实例而不是某个改进项；同一运行实例跨日安全重试或恢复时继续使用原工作分支。
- 实现 PR 标题格式为 `[AutoProgress][RUN-YYYY.MM.DD-xxxxxxxx] Implement N improvements`。
- 改进发现 PR 标题格式为 `[AutoProgress][Discovery][RUN-YYYY.MM.DD-xxxxxxxx] Add N candidates`。
- 实现批次中的每个改进项使用独立 commit；commit message 必须同时引用该改进项的完整 `IMP-...` ID 和批次共同的 `RUN-...` ID。
- 实现 PR 正文和运行记录必须列出批次包含的全部改进项 ID；不得通过分支名推断批次成员。
- 编译修复也必须先创建改进项 ID。
- 没有合格改进项的跳过运行仍拥有运行 ID，但不创建工作分支。
- 分支、commit message、PR、运行记录和运行账本必须互相引用运行 ID与改进项 ID。
- 工作分支已经存在时不得用同名分支重新实现或覆盖历史。
- 同一改进项的后续实现尝试在分支末尾增加 `-aN`，例如第二次尝试使用 `-a2`；不得覆盖或 force-push 旧尝试分支。

### 关闭未合并 PR 的重试

- 关闭但未合并 PR 不等于拒绝对应改进项。
- 后续重试沿用原改进项 ID，不得通过创建新 ID伪装成不同改进项。
- 项目策略通过 `retry.cooldown_maintenance_days` 配置自动重试冷却期，默认值为 `7` 个维护日。
- 冷却期从 PR 关闭所属维护日起计算；冷却期间不得自动重试相同改进项。
- 冷却结束后，只有采用与原尝试不同且明确说明的实现方式，才允许自动重试。
- 新 PR 必须引用原 PR、原实现未合并的原因和本次不同方案。
- 不得自动 reopen 旧 PR，也不得覆盖或 force-push 旧工作分支。
- 人工可以通过指令录入入口显式执行 `retry IMP-...`，立即跳过冷却期；该重试沿用原改进项 ID，并按人工指令项处理。
- 只有写入拒绝清单后，才永久阻止该改进项及命中对应排除规则的相似方案。

## 改动预算

- 每次维护运行默认最多实现 `3` 个具备批次兼容性的改进项。
- 项目策略通过 `batch.max_improvements` 配置单个维护批次的改进项数量上限，默认值为 `3`。
- 基线编译、原 Unity 工作区切换和最终完整验证以维护批次为单位各执行一次，不因改进项数量重复执行。
- 每个改进项仍必须分别满足自身准入、范围、风险与验收要求；多个微小项目不得合并伪装成一个改进项。
- `change_budget` 是单个普通自动改进项预算，默认维持：
  - C# 与测试文件建议上限 `3`，硬上限 `5`。
  - C# 与测试文件变更行数建议上限 `100`，硬上限 `200`。
  - 包含文档和必要 `.meta` 在内的全部变更文件硬上限 `8`。
- `batch_budget` 是整个维护批次的合计预算，默认值为：
  - C# 与测试文件建议上限 `6`，硬上限 `10`。
  - C# 与测试文件变更行数建议上限 `250`，硬上限 `500`。
  - 包含文档、运行记录和必要 `.meta` 在内的全部变更文件硬上限 `18`。
- 单项和批次预算都只设建议上限与硬上限，不设最低值；不得为了接近建议上限而扩大改动。
- 每个改进项必须满足单项预算，维护批次的所有改动合计必须满足批次预算。
- 同一文件被多个改进项修改时，逐项预算按各自 commit 的 diff 计算，批次文件数只计一次。
- 预计加入下一项会突破批次预算时停止组批，不得部分实现该项。
- 默认采用 `balanced` 数值：
  - 单项预算使用上述 `change_budget`。
  - 批次预算使用上述 `batch_budget`。
- 低于建议上限时正常执行。
- 超过建议上限但未超过硬上限时，仅当改动不能再安全拆分才允许继续，并必须在 PR 中解释原因。
- 预计超过硬上限的改进项不得开始实现。
- 实现过程中才发现会超过硬上限时，必须在 commit 前停止并报告，不得提交半成品。
- C# 文件计数同时包含生产代码和测试代码；注释与格式变化同样计入行数。
- 改进项文档和必要 `.meta` 不计入 C# 文件与行数，但计入全部变更文件数。
- 文件移动或重命名按一个逻辑文件计算，内容修改仍计入变更行数。
- 项目策略可以覆盖默认预算。预设仅用于初始化，仓库必须保存展开后的具体数值。

建议的初始化预设：

| 预设 | C# 文件建议上限 | C# 文件硬上限 | 行数建议上限 | 行数硬上限 |
| --- | ---: | ---: | ---: | ---: |
| `tiny` | 1 | 3 | 40 | 100 |
| `balanced` | 3 | 5 | 100 | 200 |
| `extended` | 5 | 8 | 200 | 400 |

在没有 Unity Editor 验证的情况下，不建议使用 `extended`。

## 拒绝语义

- 关闭但未合并自动 PR，不自动表示拒绝对应改进项。
- 只有改进项 ID 被明确写入拒绝清单，才视为拒绝。
- 拒绝记录除改进项 ID 外，必须包含拒绝原因、排除规则和适用范围；仅记录 ID 不能阻止实质相似但使用新 ID 的方案。
- 被拒绝的改进项及命中其排除规则的相似候选项，不得再次进入改进池。
- 自动 PR 必须提示审查者：如果不希望后续再次出现该方案或类似方案，需要按改进项 ID 将其写入拒绝清单，并描述需要排除的方案特征和范围。
- 日常自动维护只能读取拒绝清单，不能创建、修改或删除其中的记录。
- Codex 认为新场景可能构成合理例外时，只能提出例外申请。申请必须指明希望拓宽、修改或一次性放行的拒绝记录、理由以及精确适用范围。
- 例外申请不构成授权；在人工修改拒绝清单前，Codex 不得实现命中该排除规则的候选项。
- 拒绝清单只能由人工直接修改，或由人工明确发起一个独立的配置修改任务；该修改不得与功能代码混在同一个 PR 中。

## Unity 第一版修改边界

允许局部、低风险的 C#、Edit Mode 测试和文档改动。

默认禁止修改：

- `.unity`、`.prefab`、`.asset` 等 Unity 序列化资源
- `ProjectSettings/`、`UserSettings/`
- `Packages/manifest.json`、`packages-lock.json`
- `.asmdef`、`.asmref`
- 序列化字段的名称或类型
- 公共 API、生命周期方法及执行顺序
- 插件、平台构建配置、CI 和发布配置
- Unity/Rider 生成文件及大范围格式化

## 验证

- 每个受管项目必须由人工配置 C# 编译命令；Codex 不猜测构建入口。
- 编译配置使用一个或多个结构化步骤，每步显式包含 `program`、`args`、`working_directory`、`timeout_minutes` 和 `success_exit_codes`。
- 验证步骤不经过 shell，不允许通过字符串拼接执行多个命令。
- Codex 不得自行增加、删除、替换或猜测验证步骤。
- fetch 基准分支、取得工作区租约和开始分析不要求基准分支预先编译成功。
- 修改前必须运行一次配置的 C# 编译命令，记录基线结果。
- 基线中的明确 C# 源码编译错误应形成“恢复 C# 编译”的高优先级改进项，并优先于普通自动候选项处理。
- 编译失败源于工具缺失、依赖环境、Unity 资源、包配置或其他不可修改范围时，当天跳过并报告。
- C# 行为改动只有在该命令成功后才允许 push 和创建 PR。
- 无论基线是否成功，修改后的最终 C# 编译都必须完整通过；“没有增加新错误”不能替代成功结果。
- 基线与修改后必须使用完全相同的验证步骤。
- 任一步超时或返回未列入 `success_exit_codes` 的退出码，整体验证失败。
- 验证步骤修改受 Git 跟踪的文件时视为配置异常，必须停止；构建副作用不得混入自动 PR。
- 验证日志只在 PR 中提供经过过滤的摘要，不得泄露凭据或本机绝对路径。
- 所有验证步骤的耗时计入 `max_run_minutes`。
- 文档或纯注释改动可以不运行编译命令。
- 自动 PR 必须显著注明未经过 Unity Editor 编译、Play Mode、场景或资源验证。
- 编译失败时不得通过删除测试、降低断言或忽略错误来通过门槛。
- 创建或 push PR 不会改变基准分支；只有人工合并后，修复才进入基准分支。

### 可选 Unity MCP 验证

- Unity MCP 是后续可选集成；MCP 不可用时，PR 必须保持 Draft。
- 检测到 Unity Editor 进程并不构成验证。
- Unity Editor 必须打开当前获准使用的原始 Unity 项目目录，并在该目录 checkout 自动工作分支；其他项目路径的 Editor 无效。
- Unity MCP 必须返回并验证项目根路径，触发 Asset Refresh，等待脚本编译与程序集重载完成，并返回编译错误摘要。
- Editor 正在 Play Mode、导入未完成、桥接超时或无法确认项目路径时，验证失败。
- 编译期间出现未预期的受 Git 跟踪文件变化时，验证作废。
- 自动化必须记录通过验证的 Git tree，最终 commit 必须对应完全相同的 tree。
- Unity 编译错误为零后，可以自动把 Draft PR 转为 Ready。
- 自动 Ready 后，PR 声明改为：`Unity Editor 脚本编译已通过；Play Mode、场景和资源行为仍未验证`。
- Ready PR 后续出现新 commit 时必须重新转为 Draft；只有新 tree 再次通过相同验证才能恢复 Ready。
- Unity MCP 验证与 Ready 状态均不授予自动合并权限。
